# Customer units in standalone staging

Customers has a Units view for company-wide search and a units section within each customer record. Members can view; company owners/admins can create/edit/archive units, search and assign an available customer, clear an assignment and acknowledge duplicate-source flags. All APIs require Customers entitlement and active company membership. Customer links use a company/customer composite foreign key. Edits use optimistic versions and audit previous/new customer IDs. Original import references remain immutable when ownership or descriptive fields change.

The authorized cleaner Lightspeed export contains Customer Number, VIN 1, Make, Model and Length. No stable source unit ID exists. Each source row receives its own Marine Ops UUID. Blank/zero customer references are excluded. Known customer numbers resolve within Lakeview; unresolved nonzero references are retained as unassigned units in Needs review. Do not create omitted unnamed customers or guess owners. Repeated VINs and identical rows are retained and flagged; they are not proof that units should be merged. The existing Lightspeed customer Active flag remains informational.

Length is kept as source text, including zero; the export does not define measurement units. Year, type and unit name are optional manual fields, not inferred. Imports preserve original row fields, source customer number, file SHA-256 and worksheet row. Same-file retries skip existing rows without overwriting edits and reject changed source content at the same position. A second file hash is blocked for the company pending an explicit reconciliation workflow; no fuzzy matching or blind append across future exports. The customer_unit_imports registry serializes imports per company. Manual units remain supported.

Migration 010 adds unit storage. scripts/prepare-lightspeed-units.py uses xlrd to read the source without editing it; its JSON output must stay in ignored backups. staging/import-units.mjs is pinned to the authorized staging host and verifies every imported row, customer assignment, source snapshot and review flag. Customer/unit data never enters Git or build archives. The staging API alone exposes these routes; live Floot remains unchanged. Service Desk job selection now uses customer-owned units in staging, as described below. Storage/slip assignments remain future work.

Expected initial import: 10,312 units, 9,981 linked to existing Lakeview customers and 331 unassigned, with 25 zero-customer rows excluded. There are 1,406 source rows flagged for repeated VIN or identical contents. Needs review includes both unassigned units and unacknowledged duplicate flags, so its total is not just the unmatched count.

tests/platform-units.test.mjs covers authentication, CSRF, field validation, real PostgreSQL import idempotency, distinct repeated rows, immutable source snapshots, permissions, cross-company isolation, assignment, archived customers, version conflicts and entitlement revocation. CI uses disposable PostgreSQL. Production cutover remains separate.

## Unit selection in Service Desk

The staging New/Edit job form shows available units after a customer is selected or an existing customer link is loaded. Search and pagination are scoped to that customer. Each choice shows its VIN/serial and a short unit ID to distinguish repeated source rows. Selection fills year, make, model and hull ID/VIN from the unit snapshot. Missing values and engine details are cleared for manual entry. No engine specifications, model names or length units are inferred from other fields. Changing an unsaved customer clears its selected unit and the unit-filled vessel fields; clearing only the unit selection retains editable vessel fields as a manual job.

Migration 011 adds the persistent job/unit relationship. The staging save transaction checks Service Desk and Customers entitlements, the effective job customer, current unit ownership, available status and job version. New links to unassigned, archived, foreign-company or another customer's units fail atomically. A saved unit link cannot silently be reassigned. Ordinary checklist/manual saves omit unitId and preserve the relationship. Later unit edits, archival or ownership changes do not rewrite a historical job's vessel snapshot. The picker displays a saved link without refreshing vessel fields. Tests in tests/platform-job-units.test.mjs cover mapping, permissions, atomic failure, ownership, archive rules, version conflicts and snapshot preservation.
